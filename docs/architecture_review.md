### 가장 중요한 5가지

1. **[높음] W-1 세이브 한 칸이 손상되면 메인 메뉴가 깨진다.** 세이브가 원자적으로 쓰이지 않고(쓰다 끊기면 잘린 JSON),
   `메인메뉴화면.on_pre_enter`가 모든 슬롯을 파싱하는데 예외 처리가 없다. 재현해서 확인했다(5.1).
2. **[높음] R-2 `skill_system.py`가 가장 위험한 코드다.** `효과_적용`은 189줄/중첩 깊이 10, `공격_1회`는 매개변수 18개.
   게임 규칙을 가장 자주 바꾸는 곳인데 읽기와 수정이 가장 어렵다.
3. **[중간] W-3 수식 평가 실패를 조용히 삼킨다.** 데이터 오타가 오류가 아니라 "0"이나 기본값이 된다.
4. **[중간] R-1 `gameflow.py`가 2,296줄 / 148개 함수의 만능 창구가 됐다.** 26%(38개)는 한 줄 위임이다. 이전 로드맵(R2~R5) 이후 1,376줄에서 67% 늘었다.
5. **[중간] M-1 입구 문서가 규칙을 어겼다.** `MEMORY.md`는 40줄 이하여야 하는데 42줄/11.3KB이고, 16행 하나가 2.6KB다.

### P-1 특성 목록을 질의마다 처음부터 다시 만든다

- **위치:** `game/system/combat/traits.py:280` `_캐릭터특성_정의목록`, 호출하는 `특성_수치`(:160)·`_캐릭터특성_수치`(:356)·`속성_특성_수치`(:132)
- **근거:** 능력치 하나를 물을 때마다 `보유특성`을 훑어 토글/반응/발동조건/무기조건/방어구조건으로 거르고, 그 결과를 다시 펼친다(`_캐릭터특성_항목목록`). 전투 중 스탯 조회는 매우 잦다(`traits.py` 안 호출만 9곳, `stats.py` 8곳).
- **캐시가 안전한가(코드 확인):** 거르는 입력은 `참가자["원본"]["보유특성"]`, `참가자["장비데이터"]`(무기 타입/방어구 세트 재질), `전투상태["캐릭터특성정의"]`이다.
  `장비데이터`는 참가자를 만들 때만 정해지고(`participants.py:19`, `flow.py:75-80`) 전투 중에 바뀌지 않는다.
  `보유특성`은 `effect_engine.특성_부여/특성_제거`와 불러오기 마이그레이션(`gameflow.py:653`)에서만 바뀌고, 전투 중 호출 경로는 없다.
- **효과(측정, 시제품):** repo 밖에서 `_캐릭터특성_정의목록`에 키 기반 메모(키: 참가자 id, `보유특성` 튜플, 무기 타입, 장비데이터 id)를 씌우고 S3+S4+S6 시나리오 12개를 돌렸다.

- **제안:** 효과가 작으므로 **급하지 않다.** 하려면 참가자 생성 시 한 번 계산해 참가자에 두거나, 위 키 기반 메모를 쓴다.
  테스트가 전투 중 `보유특성`을 직접 바꾸면 값이 낡을 수 있으니 키 기반 메모가 안전하다.
- **골든 불변:** 예 · **심각도:** 낮음 · **노력:** 작음

### D-6 로컬 데이터베이스(SQLite 등)를 쓸 수 있는가

**결론: 쓸 수는 있지만 지금은 도입하지 않는 것이 맞다. 효율이 오르지 않는다.**

**측정/근거**

- 데이터량이 작다: 로드 약 60ms, 약 2.5MB. 가장 큰 컬렉션이 몬스터 29종이다.
- 조회가 단순하다: 대부분 이름으로 딕셔너리 한 번. 필터는 "개방 조건을 만족한 마을" 같은 작은 루프뿐이다.
- 프로파일에서 시간을 쓰는 곳은 데이터 조회가 아니라 특성 재계산/수식 평가다(3절). DB가 줄여 주는 비용이 없다.

| 걱정 | 영향 |
|---|---|
| 속도 | 29~수백 행에서는 SQL 파싱/조회가 딕셔너리 조회보다 느리다. |
| `buildozer.spec` | 안드로이드에서 `sqlite3`를 `requirements`에 추가해야 한다(python-for-android 지식 기준, 이 환경에서 확인하지 못함 - `NOT VERIFIED`). `requirements`가 바뀌면 CLAUDE.md 지침대로 CI 캐시 키가 바뀌어 다음 APK 빌드가 SDK/NDK를 새로 받는다(수십 분). |
| 저장소 규칙 | `file_path.py`, import 테스트, 골든 테스트, 계층 규칙이 모두 "데이터 = 파이썬 모듈"을 전제로 한다. 모두 손봐야 한다. |
| 데이터 편집 | 스킬/몬스터/특성에는 수식 문자열과 중첩 딕셔너리가 많다. 파이썬에서는 읽기 쉽고 SQL에서는 JSON 덩어리나 많은 조인 테이블이 된다. |

**DB가 맞는 경우**

- **세이브:** 전체 JSON 재작성/비원자성/손상 문제는 SQLite 트랜잭션으로 풀 수 있다. 그러나 W-1의 1~3(임시 파일 + `os.replace`, 손상 격리, 버전)이 같은 효과를 비용 없이 준다. 세이브 데이터가 훨씬 커지거나 부분 갱신/질의가 필요해지면 그때 SQLite를 검토한다.
- **데이터가 수천 행으로 커지고 드랍/희귀도 질의가 필요하거나, 코드 밖(도구, 웹)에서 편집하게 될 때.**

**더 싼 중간 방안(데이터 형식이 불편해질 때)**

- 파이썬 데이터에 스키마 검증 테스트를 건다(W-4, D-1).
- 데이터를 JSON 파일로 두되 시작 시 한 번 읽는다(여전히 DB 불필요, `include_exts`에 `json`이 이미 있다).
- 필요한 인덱스(예: 출현장소 -> 몬스터)는 시작 시 딕셔너리로 한 번 만든다.

**재검토 조건:** 몬스터/아이템이 합쳐 수천 개가 되거나, 질의 로직이 지금처럼 이름 조회가 아니라 조건 질의가 많아질 때, 또는 세이브가 부분 갱신을 요구할 때.

복잡도 측정 스크립트(핵심):

```python
import ast, pathlib


def cc(fn):
    n = 1
    for x in ast.walk(fn):
        if isinstance(
            x,
            (
                ast.If,
                ast.For,
                ast.While,
                ast.ExceptHandler,
                ast.IfExp,
                ast.comprehension,
            ),
        ):
            n += 1
        elif isinstance(x, ast.BoolOp):
            n += len(x.values) - 1
    return n


# 모든 FunctionDef에 대해 (end_lineno - lineno + 1, cc(fn), len(args.args)) 계산 후 정렬
```

### 9.2 `NOT VERIFIED` / 한계

- **화면(kivy)과 APK 빌드는 돌리지 못했다.** 이 세션에서 `tools/ui_smoke.py`(kivy + Xvfb)를 돌리지 않았다. `screens_*.py`에 대한 결론(R-4, P-5, W-6)은 코드 읽기에 근거한다.
- **안드로이드 저장소/권한 동작(W-7)과 `user_data_dir` 이전(W-1 4번)은 실기기에서 확인하지 못했다.** 권한 동작은 안드로이드 일반 지식에 근거한 추정이다.
- **`sqlite3`의 python-for-android 요구 사항 이름과 빌드 영향(D-6)은 빌드해서 확인하지 못했다.**
- **복잡도는 AST 추정이다**(`radon` 같은 표준 도구와 숫자가 다를 수 있다). 순위와 크기 순서는 의미가 있지만 절댓값은 아니다.
- **프로파일 수치는 시나리오 테스트에서 얻었고 프로파일러 오버헤드를 포함한다.** 실기기 성능이 아니다. 같은 이유로 "약 10%"도 이 환경의 테스트 시간이며 실기기 효과가 아니다.
- **전투 6.9ms는 일반공격만 쓰는 보스전이다.** 스킬을 많이 쓰는 전투(자동전투 포함)는 더 길다. 그래도 한 턴 비용은 작다고 **추정**한다(S6 캠페인 전체가 1.4~1.9초).
- **죽은 코드(D-4)는 텍스트 일치 기반이라 오탐이 있을 수 있다.** 지우기 전에 한 번 확인한다.
- **`combat` 순환이 실제로 import 순서 문제를 일으키는지는 확인하지 않았다**(현재는 동작한다). 위험은 구조적 추정이다.
- 이 보고서는 **제안이며 코드를 바꾸지 않았다.** 각 단계는 CLAUDE.md의 계획 -> 확인 절차를 거쳐 진행한다.
