### 3.3 상태 모델

**Q-2 [중간 / 보통] 전투 로그 항목에 종류 표시가 없다 (측정 + 추정)**

`core.로그(전투상태, {...})`가 남기는 dict는 `state_schema.py` 밖이다. `ctl_battle.로그_문장들`은 14갈래 `elif` 순서로 종류를 알아낸다.

```python
elif "판정" in 항목:  # 일반공격 1회, 반응 반격
elif "반응" in 항목:  # 가드/회피처럼 공격이 아닌 반응
elif "타격" in 항목:  # 스킬/몬스터 패턴/소환수 공격
...
elif "스킬" in 항목 and "지속공격 등록" in str(항목.get("비고", "")):
elif "스킬" in 항목 and "지속공격 자동 발동" in str(항목.get("비고", "")):
    ... if "판정 실패로 해제" in 항목["비고"]:
```

- 키가 *있는지*로 고르므로, system 쪽이 어떤 로그에 `"판정"` 키를 하나 더하면 앞 갈래가 그 항목을 가로챈다.
- `"비고"`의 사람용 문구가 프로그램 분기 조건이 됐다. 문구를 다듬기만 해도 로그가 "알 수 없는 항목"(`str(항목)`) 갈래로 떨어진다.
- 이 경로의 실패는 예외가 아니라 *이상한 문장*이라서 테스트로 잡기 어렵다(로그 골든이 있는 경로만 잡힌다).
- **제안:** `core.로그` 호출부마다 `"종류"` 칸(예: `"일반공격"`, `"반응"`, `"지속공격등록"`)을 넣고, `로그_문장들`을 종류 → 처리 함수 표로 바꾼다.
  "모든 `core.로그` 호출이 종류를 가진다"를 검사하는 테스트를 더한다. **로그 dict가 바뀌므로 동작 변경 커밋이다** - 로그를 담은 골든(22개)이 바뀌고,
  그 diff를 설명해야 한다. 문장 자체는 바뀌지 않아야 한다(바꾸기 전과 후 `로그_문장들` 출력이 같은지 비교 테스트).

**Q-6 [낮음 / 작음] 설정값이 화면 층 파일과 프로세스 전역에 있다 (측정)**

- 설정 파일(`설정.json`) 읽기/쓰기가 `game/screens/screens_common.py`(kivy 층)에 있다. 그래서 헤드리스 테스트로 검사할 수 없다.
  `설정_저장`은 원자적 쓰기가 아니고(세이브는 원자적 쓰기 + `.bak`), 쓰기 실패(`OSError`)를 조용히 넘긴다.
- 읽은 값은 `ctl_battle.py`의 모듈 전역 3개(`_반응_자동`, `_자동전투_방식`, `_전투로그_방식`)에 `global`로 들어간다.
  게임상태가 아니라 프로세스 상태이므로 테스트끼리 값이 샐 수 있다. 지금은 테스트가 직접 되돌려서 문제가 드러나지 않는다(추정).
- 영향: 설정 파일이 잘려도 빈 설정으로 시작할 뿐이라 데이터 손실은 없다. 그래서 낮음이다.
- **제안:** 읽기/쓰기를 system 층(예: `settings_system.py`, 새 모듈 → 사용자 결정)으로 옮기고 세이브와 같은 원자적 쓰기 도우미를 쓴다.
  전역 3개는 한 dict(`설정`)로 묶고 테스트 픽스처에서 초기화한다.

**Q-7 [낮음 / 작음] 전투 엔진 작업 스레드 (추정 - 화면이라 테스트 범위 밖)**

- `screens_battle._엔진_실행`은 반응을 묻는 모드에서 엔진을 데몬 스레드로 돌린다. 반응 팝업 콜백은 `전투상태["반응선택"]`에 *함수*로 들어간다.
  작업 스레드가 게임상태를 고치는 동안 메인 스레드는 화면을 잠가 두고, 팝업을 띄울 때만 작업 스레드가 `Event`로 멈춘 상태에서 화면을 갱신한다.
- 지금 규약으로는 안전하다. 하지만 그 규약이 코드 주석에만 있다. 같은 시간에 도는 `Clock` 콜백(예: 공격 연출)이 상태를 읽게 되면 경쟁이 생긴다.
  또 함수가 든 상태 dict는 JSON으로 저장할 수 없다(지금은 끝나면 `None`으로 비워서 문제없음).
- **제안:** 코드 변경 없이 `layers.md`에 "엔진 스레드 실행 중에는 화면이 게임상태를 쓰지 않는다"는 규약을 한 줄 적는다.
  세이브가 `반응선택`이 비어 있지 않으면 거부하는 단언을 넣는 것도 방법이다.
